Case study · Agentic AI

An agentic system, from concept to live daily use

Delivery teams spent hours each week assembling status reports, chasing anomalies across systems and pulling context from scattered documents. The goal was an agent that does the multi-step legwork and hands a person something they can act on.

  • Task decomposition. A planner breaks a request into steps, so each step can be checked and retried on its own.
  • Tool and system calls. Agents call enterprise systems and internal content through defined tools, not free-form access.
  • State across runs. Each multi-step run keeps its own state, so a partial failure does not restart everything.
  • Designed failure paths. When a step returns nothing usable, the agent says so and escalates. It does not fill the gap with a guess.
  • Outcome. In live daily use across delivery operations for automated reporting, anomaly detection and delivery intelligence.

Case study · Retrieval

RAG where every answer shows its source

Business users would not act on an answer they could not check, and auditors would not accept one. Grounding was the product requirement, not a feature.

  • Ingestion and chunking tuned to how the documents are written (minutes, logs, contracts), so a retrieved passage carries enough context to stand alone.
  • Retrieval quality measured with its own test set, separate from answer quality, so a bad answer can be traced to the stage that caused it.
  • Grounded generation. The model answers only from retrieved passages and cites each one. No passage, no claim.
  • Access-aware retrieval. Users only retrieve what they are already allowed to read.

Case study · Evaluation and monitoring

Testing before release, monitoring after

I built the evaluation practice in the AI CoE: task-level test sets, accuracy and grounding checks, and regression tests that run before every release. In production, each signal has a defined threshold and a defined response.

Case study · Guardrails

Human review placed by risk, not everywhere

Reviewing every output kills adoption. Reviewing none loses trust. I place checkpoints by the cost of a wrong answer, validate outputs before any downstream action, and give every tier a clear escalation path.

Low risk

Internal, reversible, informational output. Ships automatically with sources shown.

e.g. internal summaries

Medium risk

Output that others will rely on. Validated automatically and sampled for human review.

e.g. anomaly alerts

High risk

Client-facing, financial or irreversible. A named person approves before anything happens.

e.g. client reports, actions in systems
Practice · Model and platform choice

Not every problem needs an LLM. I choose per use case and weigh capability against cost per task, latency and where it has to run, including on-premise and air-gapped settings.

Building the team · AI Centre of Excellence

A standard path from idea to production

I set up and lead the AI CoE: reusable accelerators, integration patterns, prompt libraries and evaluation test sets, with governance built in. Every use case moves through the same stages.

  1. DiscoverScore use cases with business owners on value, data readiness, risk, regulatory exposure and time to impact.
  2. ProveBuild on reusable components. Define the test set before the prototype.
  3. ApproveGovernance gate: owner, data privacy, access control, documentation.
  4. LaunchTreat it as a product launch: sponsors, champions and training on real scenarios.
  5. MeasureTrack usage, accuracy and realised benefit against the original business case.
